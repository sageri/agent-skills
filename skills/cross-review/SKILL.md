# cross-review（外审门）

主代理始终是实现者，外审者（外部 CLI 子代理）始终只读——外审者动手就成了执行者，独立视角随之消失。

## 入口路由（第一件事）

| 用户意图 | 路径 |
|---------|------|
| 从需求做出交付物（代码类） | 全流程（下方五段） |
| 从需求做出交付物（非代码：翻译、调研、PPT 等） | 通用任务双审，读 [general-review.md](references/general-review.md) |
| 只审已有产物 | 定点门审（见下） |
| 小且低风险任务、目标清楚 | 建议直接做，说明理由并等用户表态；用户坚持时走对应流程 |

**定点门审**：跳过未点名的阶段，直接进对应门。方案/构架文档→门A；任务规格→门B；代码→门C（测试结果有则同审门D）；通用产物（翻译稿、报告、PPT 等）→门E，自审清单与送审要求读 [general-review.md](references/general-review.md)。

- 对照基准＝用户本次要求（有规格/需求文档则用文档）；自审清单第 1 条的「需求摘要」以它代入
- 被审产物非主代理所建时，改动经用户确认后进行——门审对象常是用户的外部交付物
- 落盘只建本任务目录的 `review-<gate>.md`（任务目录取法见「落盘与恢复」），不建三件套
- 结束交付**裁决汇总**（见「审核门」一节）

**完成判据**：路径已判定——全流程已进阶段1，或通用双审已定基准，或门审已定门与基准，或降级建议已提交用户表态；走双审者 task-id 已定（取法见「落盘与恢复」）。

## 流程总览

```
需求理解 → 构架思考 → 门A → 任务规格 → 门B → ★用户确认 → 实现＋测试case → 门C → 测试 → 门D → 最终报告
```

- 五道门 A构架 / B规格 / C实现 / D测试 / E产物（E 只在通用任务双审与定点门审路径上），共用「审核门」一节的机制；需求理解无门，用户就是审者
- 用户中途改向（任何路径）：停止旧流程，新要求重新定基准

## 项目 skill 接入（tdd / code-review）

两者是项目级 skill，有的项目有、有的没有。首次用到前判定一次并落盘（全流程记 `task_plan.md`，定点门审记 `review-c.md`）：项目根 `.claude/skills/<name>/SKILL.md` 或 `.agents/skills/<name>/SKILL.md` 存在＝可用。可用时 Read 该 SKILL.md 按其执行，而非经 Skill 工具调用——Claude Code 内置同名 `/code-review`（另一套正确性审查），经 Skill 工具可能调到它；内置那个不算可用。任一可用时读 [project-skills.md](references/project-skills.md)——对方 skill 里问用户、向用户展示的步骤在那里改写为落盘继续。

## 阶段

**1 需求理解** — 影响结果、范围、风险或不可逆操作的疑问集中一轮问完再继续；无疑问按最合理假设继续并写明。产物 `artifact-requirement.md`（需求摘要）：目标 / 验收标准 / 范围（must vs later）/ 假设。

**完成判据**：需求摘要四字段齐备，疑问均已获答复或写明假设。

**2 构架思考** — 产物 `artifact-architecture.md`：技术方案与取舍，含被否方案。审点：方案是否成立、有没有更简单的。

**完成判据**：门A走完——方案与被否方案已落盘，每条 finding 有裁决记录。

**3 任务规格** — 产物 `artifact-spec.md`：文件级改动清单＋测试计划＋验证命令＋done_when。验证命令在本阶段定死、阶段5照跑；仓库无测试基建时写明验证命令或手动验证步骤。tdd 可用时测试计划写成 seam 清单——tdd 要求 seam 先经用户确认，★用户确认一并确认它。审点：是否覆盖全部需求、验证是否可执行（能跑的命令，「确认没问题」不算）。

**完成判据**：门B走完，且规格获用户点头——规格阶段改错最便宜，走到测试才发现要重跑整条链。

**4 实现＋测试case** — 开工前把 `git rev-parse HEAD` 记入 `task_plan.md` 作基点（门C 的 diff 起点）。tdd 可用 → 按 tdd 在规格已确认的 seam 上逐片 red→green；不可用 → 主代理自己写测试case。审点：实现与规格一致（改动清单内的全做了、清单外的没做）、测试case 质量。

**完成判据**：门C走完——实际 diff 与改动清单一致；tdd 可用时每个已确认 seam 至少一条测试，且其先红后绿的输出行已记入 `progress.md`。

**5 测试** — 跑规格定死的全局验证命令（仓库自己的 test/build），绿了才进门D；红了回阶段4修复（修复循环不消耗审核轮次），修复后全局验证重跑。产物 `artifact-test.md`：验证命令原文＋关键输出行。审点：每条需求有测试对应用＋证据。

**完成判据**：全局验证关键输出行已贴出且为绿，门D走完。

**6 最终报告** — 按「最终报告」一节交付。

## 审核门（各门同一套机制）

**外审者**：恰好 1 名，默认 agy；用户点名时三选一（agy / claude / codex），点名优先。无头调用语法、探测与 gotcha 查 [adapters.md](references/adapters.md)。

**自审清单**（门A–D 同一张，门C 另见下条；门E 的清单在 general-review.md）：送审前逐条过，每条结果（「通过」或「已修正：…」）写进 `review-<gate>.md`。

1. 对照需求摘要逐条：每条需求都能指到本段产物的哪一部分，无遗漏、无多出
2. 边界与异常：列出失败路径、空输入、并发/重入各自的处理，或写明不适用的理由
3. 验证方式可执行：能跑的命令、能看的证据
4. 可追溯：每处新增/改动都追溯到用户的一条要求

**门C 自审**：code-review 可用 → 按 [project-skills.md](references/project-skills.md) 执行；不可用 → 过上方清单。

**送审包**（自包含，外审者不继承主代理上下文）：

```
外审者 persona：只读，不改文件；只用内置工具，禁止调用任何 MCP 工具
需求摘要＋该阶段产物（路径一律绝对路径）
代码上下文/diff 指引（门C必附 diff）
审点
```

组装前重跑一次 `git status`；被审产物与附带的 diff 从同一 commit 取（`git show <commit>:<path>`）——并行会话可能在门审中途移动工作区，跨 commit 混装会把自相矛盾的包送出去。产物不在 git 里（用户外部交付物）则直接取文件。

送审包一律先写临时文件再传（claude/codex 走 stdin）。外审者为 agy 时，产物内容一律内联进包（附行号）——agy 拒绝点前缀路径；包超 30K 字符时，打包前先读 adapters.md 的 agy 段（文件通道要求包末校验串＋SECTION 分块，回复先过 Read-Check）；预估超 5 分钟传 `--print-timeout`（均见 adapters.md）。

**审核结果**（只认这个结构；解析不出合法 `Status` → 判失败走降级链）：

```
Status: PASS | CONCERNS
Findings:
- [P1|P2|P3] 问题描述 — 证据: 文件:行号
（PASS 时 Findings 写 None）
```

每次外审回收后，把该次调用的 usage 原生数据记入该门的 `review-<gate>.md`（字段来源见 adapters.md）。

**裁决**：每条 finding 逐条写「采纳 / 驳回＋理由」到 `review-<gate>.md`；任何级别都可驳回，写明理由即可。每门最多 2 轮外审：第1轮意见→裁决与修改→改动重大时第2轮复核（「改动重大」＝推翻该阶段产物的主要方案）；第2轮后仍有 P1 分歧 → 带双方意见问用户。

**裁决汇总**（定点门审与通用任务双审的结束输出）：每条 finding 采纳/驳回＋理由、改动清单、外审者与 usage。

**降级链**：外审 CLI 失败/超时 → 重试 1 次 → 换外审者（顺序 agy→codex→claude，起点＝本次选定者；点名者被换须在最终报告注明，如「codex→claude」）→ 全失败则该门仅自审，最终报告标注「本门无外审」。降级链走到底，流水线照常推进。

## 落盘与恢复

- 任务目录＝`.cross-review/<task-id>/`，一次双审一个：三件套、产物、门审记录全部落其中，并发会话各占各的目录互不覆盖。task-id 取用户话里的任务标识——issue/PR 号（如 `issue-35` / `pr-35`）优先，无号取任务短名 slug，再无则日期＋slug；同一任务重开复用同一 task-id；分支名不作 id（共用工作树的并行会话读数相同）
- planning 三件套（`task_plan.md` 追踪阶段与门的状态 / `findings.md` / `progress.md`）——一律落任务目录：优先调用 `planning-with-files` skill，按其方法与模板运作、以本任务目录为其 selected task directory（不走其 init-session/.planning 机制）；本地无此 skill 时由主代理自行创建同名三件套（普通 markdown，落盘不可省），落点相同。三件套仅主代理可写，中断恢复靠它
- 产物与门审记录也在任务目录：`artifact-requirement / architecture / spec / test` 四个产物＋每门一份 `review-<gate>.md`（自审结果、送审包、结果原文、裁决记录、usage）；保留到用户确认交付后再清理——裁决记录是可追溯凭据
- 中断恢复：重读任务目录的既有落盘（全流程从三件套起头；定点门审与通用双审读该门的 `review-<gate>.md`），从最后未完成的阶段/门继续；全局验证之后任何文件再变，全局验证重跑

## 最终报告

| 字段 | 内容 |
|------|------|
| 阶段状态表 | 每阶段：完成 / 降级 / 仅自审；阶段4 标 tdd / 自写，门C 自审标 code-review / 清单 |
| 审核摘要 | 每门：谁审 / PASS 还是 CONCERNS / 几条采纳几条驳回 / 降级事件 |
| 全局验证 | 命令原文＋输出关键行（测试统计行、构建结果行）；转述式「全绿」不算 |
| usage | 各门 `review-<gate>.md` 里的无头调用用量，原样展示原生数据 |
